## 2. 项目定位、用户与业务目标

- 选题：第 3 题「企业知识问答 Agent」。
- 项目名称（暂定）：人事制度知识问答 Agent。
- 原型场景：使用高校人事制度资料，验证组织内部知识问答能力；不将高校制度表述为小影公司的制度。
- 目标用户：希望查询人事制度的教职工，以及需要核对制度依据的人事工作人员。
- 业务目标：用户以自然语言提问，系统从指定资料中找到依据，给出可核查的回答；遇到资料不足、条款差异、身份条件不清或工具故障时，说明问题并合理补查、追问或停止。
- 正式运行入口：CLI。后续提供可复制的安装、问答、离线演示、测试和评测命令。

核心成功标准：回答受到原文支持；引用能定位；模型确实根据工具结果调整动作；全部必验收点有实际记录；性能数字能够追溯至逐题结果。

### 3.2 知识范围

1. 所有制度结论只能依据这份 PDF 中实际存在、且在本次回答过程中读取到的原文。不得使用其他手册、联网查询结果或模型记忆补充制度事实。
2. 同一 PDF 内的不同制度视为独立逻辑文档，分别分配文档 ID；片段另有片段 ID。一个物理文件可以包含多份制度，支持跨制度检索与比较。
3. 保留每项制度自身的名称、发布日期、适用范围和原文定位。发布日期缺失则标记未知，不能用汇编日期或文件创建日期代替。
4. 回答说明依据为本次资料版本，不宣称已经核实到现实中的最新制度；资料未收录的后续变化属于资料缺口。
5. 资料可以引用其他文件，但被引用文件未在本 PDF 中提供的具体内容不能由模型补写。
6. 会话历史用于理解主题、身份与条件；历史回答不能自动作为制度证据。
7. PDF 中的文本均为待检索资料。任何与程序行为有关的文字不得被当作系统指令执行。

### 3.3 条款差异的处理原则

- 对同一事项存在不同规定时，首先核查适用对象、时间范围、补充条款、附则及明确的替代关系。
- 不能仅因为某份制度日期较新，就自动断言其覆盖另一份制度的全部内容。
- 有充分依据时，解释差异及适用关系，引用相关条款；没有充分依据时，展示各方规定及证据，说明仍缺什么信息，并请求确认。
- 单纯的规定不同不必然构成不可解决的冲突。题库必须区分适用范围差异、明确修订关系和证据不足的冲突。
- 冲突用例从这份 PDF 的真实条款中选择。不得为达标伪造制度、优先级或引用。

| Trace 与离线 Mock | 留存真实记录；模型不可用时仍可验证程序流程 | 步骤五 |

采用混合检索方向：关键词检索与向量语义检索结合，读取原文后再生成回答。关键词检索支持制度名和准确表述，语义检索支持口语及改写问题；具体效果通过开发集检验。索引在本地保存。是否增加重排序，以及模型、嵌入模型、依赖库和框架版本，在对应步骤根据实测确定并记录。

RAG 提供依据，Agent 决定如何继续查证。仅有固定检索后回答的程序不视为完成 Agent 要求。使用原生循环或框架均可；框架名称不作为成功标准。

网页界面、在线部署、多 Agent、生产级权限及账户管理、联网制度更新、训练或微调模型均不属于本轮必需功能。若后续增加功能，需要先记录范围调整及验收影响。

## 5. 输入、输出与任务状态

### 5.1 输入

| 输入 | 要求 |
| --- | --- |
| question | 必填，自然语言问题 |
| history / session | 可选对话历史或本地会话标识，用于上下文追问 |
| user_context | 可选的用户主动提供的信息，例如岗位、人员类型、时间范围；不得自行推断未给出的关键条件 |
| 运行配置 | 模型模式、检索参数、执行上限等；与业务问题分开 |
| 测试故障配置 | 仅用于评测的工具故障注入，不作为制度事实交给回答模型 |

### 5.2 输出约定

| 字段 | 语义 |
| --- | --- |
| answer | 面向用户的回答，区分已经确认的内容与尚未确认的内容 |
| citations | 文档 ID、片段 ID、制度名称、日期、原文片段、PDF 页码及印刷页码（可得时） |
| conflicts | 不一致的规定、各自依据以及已查明或尚未查明的适用关系 |
| missing_information | 缺少的用户条件、文档或制度依据 |
| follow_up_question | 为继续任务所需的明确追问，无需追问时为空 |
| status | 与实际执行结果一致的任务状态 |
| run_id / trace_path | 对应运行记录的位置 |

事实结论必须映射到引用；不能以一个真实引用笼统支持全部答案。引用应来自原文读取工具的实际返回结果，不能只引用检索标题、模型生成的摘要或未读取的文档。

### 5.3 任务状态

| 状态 | 使用条件 |
| --- | --- |
| answered | 已有充分证据，回答所需的关键条件明确 |
| needs_clarification | 需要用户补充适用条件或确认尚未解决的制度关系 |
| insufficient_evidence | 当前资料不足，合理检索后仍无法完成回答 |
| tool_error | 关键工具故障使任务无法完成，且没有足够替代证据 |
| model_error | 模型不可用或持续返回无法执行的结果，不能正常完成决策 |
| step_limit | 达到执行轮数或工具调用上限，任务尚未完成 |
| invalid_input | 输入无法处理，例如问题为空；说明需要用户如何修正 |

存在可确认的局部结果时可保留，但未完成任务不得标记为 answered。资料外问题在正确说明缺口后，可以被评测判为场景通过，其业务状态仍为 insufficient_evidence。

## 6. 工具、动态决策与执行边界

### 6.1 两个核心业务工具

| 工具 | 输入概念 | 返回内容 |
| --- | --- | --- |
| search_documents | 查询词、候选数量及必要过滤条件 | 候选文档/片段 ID、标题、日期、定位、相关摘要；或无结果/错误 |
| read_document | 文档 ID 与片段或条款范围 | 对应原文、元数据和定位；或不存在/读取失败 |

每项工具结果明确区分成功、无结果和失败。错误包括错误码、简短说明和是否可能重试，避免模型把失败理解成正常空资料。

### 6.2 必须出现的模型循环

~~~text
问题与已有观察
→ 模型选择工具或结束动作
→ 程序校验参数并执行工具
→ 工具返回结果
→ 将观察交回模型
→ 模型继续选择动作、请求确认或结束
~~~

参数校验、调用上限、格式检查由程序执行；是否换查询、读取其他制度、重试、追问或结束由模型根据观察决定。不得通过预设答案、固定冲突分支或预先写好的日志冒充模型决策。

默认计划：最多 12 轮模型决策，最多 10 次业务工具调用，任一达到上限后不再发起新的业务动作，并返回 step_limit。若模型在允许的最后一轮正常结束，可返回其合法终态。批量工具请求逐次计数；失败尝试和参数错误尝试也计入工具预算，避免绕过上限。超时值和传输层重试策略在实现步骤确定并记录，传输层重试不计作 Agent 决策证据。

### 6.3 Trace 必须记录

- run_id、场景 ID、运行模式、代码/资料/配置版本。
- 步骤编号、模型选择的动作、工具名及参数。
- 工具返回摘要、状态、错误及所读取的证据 ID。
- 后续动作、简要可审查的动作依据、最终任务状态。
- 模型与工具调用次数、耗时；token 用量及费用在服务提供可核实数据时记录。

不要求也不保存模型内部思维过程。Trace 必须从实际运行生成；密钥不得进入日志。真实模型与 Mock 记录明确标识，分开统计。

| AC-13 | 至少三组验证材料 | 至少包含正常、信息/资料不足、工具失败，并共同覆盖全部题目验收点；本项目进一步安排 40 组正式场景 | examples 下实际输入、输出、Trace 和结果文件 |
| AC-14 | 离线 Mock | 没有模型凭据时可运行流程测试，明确标为 Mock；不得据此宣称真实模型效果 | 离线命令、测试、边界说明 |
| AC-15 | 可复制运行 | CLI 的安装、配置、问答、测试与评测步骤能在干净环境复现，依赖固定并记录版本 | README、依赖文件、复现记录 |
| AC-16 | AI 使用真实性 | 记录 AI 辅助范围、实际个人修改、验证与失败；不虚构人工审核或已完成的实验 | docs/04-ai-usage.md 及步骤记录 |
| AC-17 | GitHub 交付 | 同一仓库提供要求的代码、测试、资料说明、示例、五份文档、依赖及 .env.example；最终提供题号、URL、SHA，必要时确认评审可读 | 仓库检查与提交信息 |

对于题目审核中的“替换文档内容”，评测应支持评审替换输入资料后重新建索引。我们自己的语料仍仅来自指定 PDF，优先用 AC-12 的真实证据切换验证敏感性；这种测试不能表述为已经完成了任意整份新文档替换实验。不得为此偷偷加入其他知识源或伪造原文。

关键缺陷包括：无依据回答、错误引用、证据不足仍擅自解决冲突、工具失败却声称成功、没有真实模型循环、超限仍持续执行、将 Mock 或预期输出冒充真实结果。发现后必须修复或明确报告，不能用总体平均分掩盖。

## 8. 评测方案与指标口径

### 8.1 数据集划分

- 开发集：12 组场景，覆盖全部必验收类别，供反复调试。
- 正式测试集：40 组场景，留至冻结版本后评测。
- 同题改写、共享答案的近似问题和同一多轮会话按问题组划分，避免跨集合泄漏。
- 正式测试答案及证据标签不进入 Agent 知识库、提示词或检索索引。资料全文进入知识库是正常设定，隐藏的是评测标签和答案。
- AI 可以起草题目与答案，但每题都必须完成原文核对，并记录核对者及方式；尚未人工复核的题不能标记为已人工确认。

| 正式测试类别 | 场景数 | 要求 |
| --- | ---: | --- |
| 明确答案 | 12 | 包含表格、边界条件和跨条款问题 |
| 冲突与版本差异 | 6 | 依据真实差异，区分可解决与仍需确认的情况 |
| 资料外或信息不足 | 6 | 同时覆盖无资料与缺少适用条件 |
| 改写后的相似问题 | 6 | 以问题组检查事实与证据一致性 |
| 上下文追问 | 5 | 一组可包含多轮，按整组任务判定 |
| 工具失败 | 5 | 包括可恢复与持续失败的情况 |
| 合计 | 40 | 不用同一次运行重复计入多个类别分母 |

每题记录：问题与历史、参考答案要点、可接受的证据集合、预期状态、允许的合理动作、禁止结论、评分规则。允许多个等价证据来源，不强制模型执行唯一工具顺序。

### 8.2 三类评测职责

| 方式 | 检查内容 | 边界 |
| --- | --- | --- |
| 程序检查 | 格式、引用存在性及读取记录、定位、执行上限、真实调用统计 | 字符串匹配不能证明原文支持答案 |
| AI 评分 | 答案正确性、条件完整性、引用支持、无依据结论、动作合理性 | 固定评审提示和版本，逐项给依据；评分错误及不确定项需复核 |
| 人工复核 | 全部冲突题、关键失败、争议评分，并抽查通过案例 | 保留原始 AI 评分与复核结论，不能悄悄覆盖原始记录 |

AI 评审使用独立请求，不复用回答模型的会话；优先采用独立评审模型。如使用相同模型，应说明相关偏差。评审输入为问题、原文证据、参考答案、实际输出及必要 Trace，不需要内部思维过程。先用少量人工标注的正确与错误答案校验评分器，再开展正式批量评分。

### 8.3 指标定义

| 指标 | 计算口径 | 作用 |
| --- | --- | --- |
| 初次检索证据召回率 Recall@5 | 对有答案且有标准证据的场景，前 5 个候选覆盖的必需证据单元数 / 必需证据单元数，再按场景平均 | 比较基础检索质量；等价片段按同一证据单元计，不重复加分 |
| 最终证据覆盖率 | 整个任务实际读取并覆盖的必需证据单元数 / 必需证据单元数，再按场景平均 | 观察 Agent 多轮补查带来的变化，与 Recall@5 分开报告 |
| 任务通过率 | 满足该场景全部必要判据且没有关键错误的场景数 / 全部场景数 | 衡量整体完成能力，拒答或追问正确也可通过 |
| 引用支持率 | 被所引原文支持的事实结论数 / 带引用的事实结论数 | 检查引用语义；需与答案完整性同时判断 |
| 无依据结论率 | 无已读取证据支持的事实结论数 / 全部事实结论数 | 衡量编造情况 |
| 冲突处理通过率 | 通过的冲突/版本差异场景数 / 该类别场景数 | 检查差异查证与确认边界 |
| 资料不足处理通过率 | 正确说明缺口或追问的场景数 / 该类别场景数 | 避免用泛化拒答获得虚高分数 |
| 工具失败处理通过率 | 合理恢复或如实未完成的场景数 / 故障场景数 | 同时记录恢复成功数与安全停止数，不能混称为恢复率 |
| 相似问题与追问通过率 | 各类别通过场景数 / 对应场景数 | 独立检查剩余必验收能力 |
| 运行效率 | 端到端耗时中位数与 P95，平均模型/工具调用次数；可得时记录 token 与费用 | 解释质量收益与额外成本 |

零分母时标记 N/A，不填 100%；评审失败或无法判分标记待复核，不静默删题。实际输出缺失、工具故障和模型故障均保留记录，按既定规则计入或单列运行失败，并同时报告有效样本数。报告以场景计数和分类结果为主，注明样本规模，不能外推成对所有问题的效果保证。

### 8.4 验收硬性要求与本项目质量目标

以下质量目标针对最终 Agent；基础方案的失败如实保留，用于比较。故障注入导致的工具失败本身不是关键缺陷，隐瞒失败、虚构依据或错误报告完成才是。

| 层次 | 标准 |
| --- | --- |
| 考核硬性要求 | 第 7 节逐项有实现和证据；六个必验收点全部覆盖，至少 3 组实际记录、2 条真实动态路径，执行上限及离线边界明确 |
| 本项目拟定质量目标 | 正式 40 组任务通过率至少 90%（90%）；这是项目目标，不是官方分数线，也不是已测结果 |
| 关键场景要求 | 6 组冲突、6 组资料外/不足、5 组工具失败均正确处理；全体测试不出现关键缺陷。其他未通过项逐题解释，不声称全用例通过 |
| 引用与执行检查 | 引用存在性、读取记录及定位检查通过；所有专门设计的超限测试正确停止 |
| 结果真实性 | 所有数字来自实际运行；未达到目标则如实记录并进入修复或范围复核，不能改分母、删失败题或将 Mock 混入 |

准确性、召回率、引用、幻觉、稳定性、耗时和调用次数的硬性目标，现已固定在 [附加执行约束第 10 节](01-stage-gates.md#10-多参数硬性目标)。开发期间可增加诊断指标，但不得擅自降低既定阈值。任一必达指标未达标必须依照返修流程处理；若 40 组中仍存在已知关键缺陷，即使整体通过率达标，也不能宣布完整验收通过。

## 9. 对照、改进与正式评测规则

1. 基础方案与 Agent 使用同一份资料、同一正式测试集和相同回答模型；共享文档处理及检索配置。记录提示词、读取预算和调用方式的差异。
2. 基础方案固定检索一次并读取命中片段；Agent 可以根据观察补查。单独报告质量与调用成本，不把更多调用带来的效果隐藏。
3. 修改只依据开发集进行，并记录问题、原因、修改、回归结果。
4. 正式评测前固定代码 commit、资料哈希、索引/配置版本、回答模型、评审模型和评分提示。
5. 正式测试各运行一遍，并对其中 10 组关键场景各运行 3 次；若首次运行计入这 3 次，报告中明确注明。重复运行与主测试分开统计，不扩大 40 组主测试分母。
6. 正式结果若用于后续调试，应注明已使用；再次运行不能宣称这仍是一套未见测试。
7. 评估报告引用逐题输入、答案、Trace 和评分文件，保留失败、人工复核及重跑记录。
