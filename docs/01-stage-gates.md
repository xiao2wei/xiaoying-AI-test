## 1. 必须遵守的总原则

1. **目标未全部完成，不得进入下一步。** 写完代码、跑通一次、完成部分测试，都不等于完成该步骤。
2. **有产物、有验证、有实际证据，才可判为完成。** 每项检查记录通过、未通过或待验证，并引用实际文件；无证据视为未完成。
3. **达到目标后自动进入下一步。** 用户已在 2026-10-30 明确授权按目标连续推进，不再逐步请求批准；未达标必须返修。本轮授权止于步骤八，步骤九 GitHub 交付暂缓。需要真实人工核对的事实不能因自动推进授权而伪造。
4. **每步都要有 Markdown 记录。** 包含目标、实现、产物、执行命令、环境、实际结果、失败与修复、限制、AI 辅助、实际人工操作及用户审阅状态。
5. **任一必达指标未达标，就返修。** 必须先定位原因，再修改，经过针对性验证和完整回归后重算全部指标；不得只重算之前失败的那一项。
6. **多指标同时达标，不用总分抵消短板。** 召回率高不能抵消幻觉，回答正确不能抵消错误引用，安全拒答不能抵消对可回答问题的不当拒答。
7. **不擅自降低标准。** 不删失败题、不改分母、不缩小知识范围、不改变评分口径、不放宽阈值、不选择有利运行作为最终成绩。确需改变目标，必须说明影响并取得用户明确同意。
8. **只使用指定 PDF 作为制度知识来源。** 保留原文与来源，不添加外部制度，不伪造冲突，不把模型知识当作证据。
9. **真实运行与 Mock 明确区分。** Mock 只证明程序流程；真实模型决策、真实模型质量和真实 AI 评分必须有真实调用证据。
10. **参考答案与评分器也需要验证。** 不能以错误标签强迫系统答错，不能用评分器自评代替校验；人工复核必须确实由人执行，不得将 AI 检查标成已人工审核。
11. **正式测试保持可追溯。** 在看到正式结果之前冻结配置。正式结果用于返修后，该集合标为已使用的回归测试集，仍保留原始 40 组，不再声称是未见测试。
12. **外部条件不足时保持未完成。** 如模型不可用、缺凭据、缺人工确认或预算不足，应明确指出缺口；不得用虚构结果、Mock 或口头承诺代替达标证据。
13. **返修允许回到已批准步骤。** 在既定范围内修复并验证，不需要为每次例行改错重复请求许可；修复影响的下游产物必须重建和复测。进入新的步骤仍遵守第 3 条。
14. **“完成”仅描述已经验证的当前版本。** 过去失败保留，修复版本的结果单独记录。固定测试集上的通过不等于对任意未来问题的质量保证。

## 10. 多参数硬性目标

以下阈值由本项目制定，作用于固定评测范围内的最终 Agent，不是考核方官方分数线，也不是已测结果。每项均必须单独满足，不得以加权总分替代。除正式样本数量与稳定性要求外，适用的质量指标也用于开发集；开发集任务通过率采用更严格的 12/12。

| ID | 参数 | 正式评测必须达到的目标 | 统计与防误用规则 |
| --- | --- | --- | --- |
| M01 | 初次检索证据召回率 Recall@5 | ≥90% | 对具有标准证据且应检索的场景，按必需证据单元计算首轮前 5 个候选覆盖率，再按场景平均；多轮场景先按需检索轮次平均；同义片段不能重复加分 |

补充规则：

- M01、M02、M04、M05 的适用场景名单和标准证据在评测前确定；报告同时给出名单、场景数、逐题分数及聚合结果。
- M06 至 M08 以原子事实结论为单位，冻结拆分与判定规则。人工复核改分需要记录理由及原文，保留原分。
- 分母为 0 时记 N/A，不得当作通过。正式集应该提供的评测对象缺失时属于题库或评测缺陷，须修复。
- 模型服务实际失败或超时必须记录，不能为了耗时达标删除慢请求。能确认的外部故障可以在服务恢复后完整重跑，但原结果保留，不能只替换慢题。
- 小样本类别同时展示通过数/总数；100% 仅指该批测试，并不代表所有未知输入都正确。
- token 用量、费用、冷启动和索引构建耗时也应记录；服务未提供可核实信息时标明缺失，不编造费用。费用预算在实际模型选定后固定。
- 本表是项目必须达成的目标。达不到时保持未完成并返修；需要更改模型或预算时说明实际缺口。不得在观察正式结果后自行把阈值降低。

## 11. 未达标必须执行的返修闭环

~~~text
发现任一指标不达标
→ 保留本轮完整结果，标记未通过
→ 定位失败场景和错误位置
→ 根据证据确认根因
→ 制定并实施修复
→ 对失败场景和相邻边界做针对性验证
→ 完整运行开发集与相关程序测试
→ 冻结新候选版本
→ 完整重跑正式集及预定稳定性测试
→ 重算全部指标
→ 全部达标并经用户审阅后，才推进
~~~

### 11.1 根据指标定位原因

| 未达标表现 | 首先核查 | 允许的修复方向 | 复测重点 |
| --- | --- | --- | --- |
| Recall@5 低 | 原文是否漏提取，切分是否割断语义，关键词/语义检索哪一路漏召回，融合排序是否压掉另一制度 | 修复提取或切分、查询归一化、混合召回与融合、必要重排序 | 保持 K=5 重新测量；不得把 K 改大后仍写 Recall@5 |
| 最终证据覆盖不足 | 是否只读第一条，补充规定是否遗漏，候选摘要是否不足，调用预算是否被无效动作耗尽 | 改进检索工具返回、上下文展开与模型补查指引 | 必需双方证据、跨页条款、引用链和调用次数 |
| 幻觉或答案错误 | 是否误读表格、混淆年份/适用对象、漏掉否定和例外、把未提供的外部规则当事实 | 修复资料结构、证据与结论映射、生成约束和不足时的状态处理 | 幻觉、正确率、完整度一起测，避免退化为一律拒答 |
| 引用不支持或定位错 | 片段是否错绑文档/页码，引用是否未实际读取，结论是否超出原文 | 修复引用数据、定位映射和输出校验；保留原文 | 语义支持与机械校验同时检查 |
| 冲突处理错误 | 是否漏读另一条款，是否把较新日期当作完整替代依据，是否忽略身份范围 | 修复补查机制、适用关系判断与确认边界 | 可解决差异及不可确认情形都回归 |
| 相似问题/追问差 | 同义表达、指代、身份和时间条件是否丢失 | 改进检索与历史消息组织 | 同组所有问法及完整会话，不只测单句 |
| 故障处理失败 | 错误是否被当作空资料，模型是否观察到错误，循环是否重复无效调用 | 规范错误返回、恢复选择、终态及计数规则 | 可恢复、持续失败及上限场景 |
| 耗时或调用次数超标 | 检索、读取、模型推理和重复动作分别耗时多少，返回上下文是否过大 | 优化索引读取、上下文长度、合法缓存和重复动作控制 | 正确率、证据覆盖、冲突处理必须同时维持，不得跳过必要查证 |
| AI 评分不可信 | 标准答案、原文证据、评分提示和事实拆分是否错误 | 修复评测器与标签，做人工确认和重新校准 | 基础方案与 Agent 按同一修正口径重新计分 |

不得在查清根因前，用替换期望答案或大量追加针对某题的硬编码来消除失败。可以改变实现方式，但不能把标准答案表或测试 ID 判断塞入回答逻辑。

### 11.2 每次返修必须记录

- 缺陷编号、发现版本、场景 ID、未达标指标及实际值/目标值。
- 原始输入、输出、工具观察、证据位置和 Trace 路径。
- 根因分析及支持证据，不能只写“模型不稳定”。
- 修复内容、影响范围、代码/资料/索引/提示或评审版本变化。
- 针对性验证、完整开发回归、正式回归与稳定性结果。
- 所有指标的修复前后对照，是否引入新退化。
- 参考答案或指标口径确实有错时，保留原版本并给出修正依据；不能为了系统得分改成错误答案。
- 当前结论：未通过继续返修、待外部条件、或全部达标待用户审阅。

若数据处理或检索实现改变，重建索引，并使基础方案与 Agent 使用相同修复后的资料和检索配置。以前的对照报告留存，不覆盖。
