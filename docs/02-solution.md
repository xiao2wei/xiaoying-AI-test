# 实现方案

## 主链路

用户问题与实际会话历史 → DeepSeek选择search/read/finish → 本地工具执行 → 模型观察成功、低相关候选或错误 → 补查/读取/追问/结束 → 引用程序校验 → 最终回答与Trace。

基础RAG共享同一资料和检索器，只固定查询一次、读取5条、生成一次，用作对照。框架使用原生Python，职责明确，未引入多Agent服务或线上发布。

## 资料与检索

PDF按29份独立制度切分，保留版本日期与双页码。条款片段为562个，向量化使用1138个重叠窗口映射回原条款。真实中文BGE向量与BM25分别排序，RRF20融合后固定返回5个候选。语义模型512维、本地CPU运行；全文和表格仍在原文库，检索窗口不取代引用原文。

## 决策与约束

决策来自真实DeepSeek的JSON动作，工具函数没有测试ID分支。模型可以改写查询、过滤文档、批量读取或停止。批量每个读取ID分别计数，默认整组最多10次业务工具尝试、12轮决策；失败与参数错误也计数。HTTP请求重试与业务决策分开记录。

回答包含status、原子结论claims、逐结论引用citations和资料缺口gaps。引用必须来自本次实际read结果，quote逐字匹配（只允许空白归一化），页码和日期由程序绑定原始元数据。机制不直接证明语义正确，独立评分器再判断引用支持、遗漏条件与幻觉。

资料只有版本差异而无明确适用关系时列出双方并追问；明确废止条款可以解决关系；用户指定历史版本时依该版本回答。绝不把较新日期直接作为优先证据。

## 评测隔离

问答模块只加载data/processed/chunks.json和索引；evaluation中的金标仅用于批处理输入和独立评审。正式题库已在v1起实际运行并参与返修，后续结果属于已曝光题库回归，不能声称未见测试；改写/同一事实按族划分，不跨开发正式集合。评分器使用独立上下文和不同的DeepSeek模型。人工标签导入不由AI自动填写。

## 已知问题

早期开发首轮Recall@5为85%，后续候选已达到95%；16项真实人工标签已确认且校准16/16。当前candidate-v4的138轮评分已完成，Agent36/40、稳定性27/30，用户已接受指标及完整复核清单。已知失败和3个关键缺陷场景标记保留，见SUBMISSION.md；不再追加优化。

## 正式测试返修后的最终核对

首次合法finish后，增加一次同一DeepSeek回答模型的thinking核对。该真实请求纳入模型次数和端到端耗时，仍受整组12轮/10工具预算约束。核对可保持、修改回答或决定补读；其输入只有问题、历史、已读证据、工具观察和初稿，没有标准答案。评审仍为独立Pro模型，不将该核对当作AI评分。

## 格式恢复、请求控制及通用问题边界

合法JSON不改值；仅恢复多余右括号及完全重复对象。不同对象或预演工具结果不执行。常规动作仍用json_object；格式失败才在同一最多2次HTTP预算内使用三个简单函数的严格格式重试，禁用思考以兼容强制tool_choice。实际接口返回仍需本地验证，strict不是本项目实测的无错误保证。最终核对首请求维持启用思考，格式重试单独记录实际模式。

通用制度、指定版本或给定边界问题直接回答原文规则，不把它强行变成个人资格审批。个人实际待遇缺必要条件才追问。只读取真实返回的候选ID，按剩余业务工具次数限制读取批量，冲突查证集中于双方与解释衔接条款。

真实评分只在输入、提示、模型、思考模式与配置完全同哈希时复用；失败评分也同样复用，不挑高分。用户仅允许确定性格式修复复用未受影响问答记录；本轮策略调整须完整真实回归。校准、开发、正式分阶段执行，发现前置失败即不启动后续大批量请求。
